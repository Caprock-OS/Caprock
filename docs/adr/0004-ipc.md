# ADR 0004 — IPC

**Status:** implemented (core) · **Date:** 2026-06-23

> **Implementation status (phase 5):** synchronous **endpoints** (Call/Recv/Reply) are
> implemented (`crates/caprock-ipc` + `caprock-abi`): SVC syscall entry,
> register-based messages, block/unblock via the scheduler, rendezvous with
> direct switch (fastpath idea). **Still open:** notifications, non-blocking
> `Send`, capability transfer in messages, zero-copy payload via memory cap,
> and — important — **cap-guarded endpoint access** (per-thread cspaces, phase 6).
> See `docs/phase-reports/phase-5.md`.

## Motivation

IPC is the central communication base. Goals: low latency, good
multicore scaling, suitability for hot-reloadable components.

## Reference: the seL4 model

Synchronous **endpoints** (sender/receiver rendezvous), asynchronous
**notifications** (badge signals), **reply** objects (MCS) for call/reply, and
a **fastpath** that shortens lookup/scheduling when conditions are met.
Capability transfer carries rights as part of the message. Details:
[`../seL4-architecture-map.md`](../seL4-architecture-map.md).

## Caprock-specific opportunity: SAS lowers IPC cost

Because there is a single address space (ADR 0002), every address is valid for every
receiver. This opens up **zero-copy IPC**: instead of copying payload,
a **memory capability** (move/borrow) is passed. That is the biggest
latency lever compared to classic IPC buffer copying.

## Approaches analysed

### A) True to seL4: register/IPC buffer copy for small messages
- **+** Simple, proven for short messages (few registers).
- **−** Copy cost for larger payloads.

### B) Capability/reference-based zero-copy for payload (chosen, complementary)
Small control messages continue via registers (fast); larger payload as a
transferred **memory cap** (zero-copy, thanks to SAS).

- **+** Very low latency for large transfers; deterministic.
- **+** Fits the cap model (transfer is a cap move).
- **−** Lifetime/ownership rules for the passed region are needed (secured via
  the CDT).

### C) Multicore: per-endpoint locality instead of global locks
Endpoints/queues are kept **core-local** where possible; cross-core IPC
uses targeted IPIs instead of global locks.

- **+** Scales to 8 cores, avoids global contention.
- **−** More complex state machine for cross-core rendezvous.

## Decision

Endpoints + notifications + reply on the seL4 model, **extended** by
zero-copy payload via memory-cap transfer and by core-local endpoint states
with IPI-based cross-core delivery. A fastpath accelerates the frequent
call/reply case (resolved cap cached, direct transition to the receiver without a
full scheduler pass). For hot reload (ADR 0006): endpoints are named objects
addressed via capabilities whose *identity* survives a
component change (re-bind instead of reconnecting).

## Security implications

Capability transfer = explicit, checkable passing on of rights (no ambient
authority). Zero-copy regions are monitored by the CDT; rights withdrawn after a transfer
can be enforced via revocation.

## Performance implications

Fastpath + zero-copy aim at IPC latency close to a function call for small
messages and at constant cost independent of payload size. Core-local
endpoints + IPIs ensure multicore scaling and determinism.
